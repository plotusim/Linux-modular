# v40：LLVM 回调表互补组合自动模块化

## 阶段结论

本阶段已经把两个原本内建、且不受普通 Kconfig 模块选项控制的函数闭包，
通过完整 LLVM 引用图自动提取为新模块：

- `fs/proc/base.c`：13 张常驻操作表、20 个惰性回调入口，闭包共移动
  25 个 C 函数定义；
- `drivers/dma-buf/sync_file.c`：1 张常驻操作表、2 个惰性回调入口，
  闭包共移动 10 个 C 函数定义。

两个模块分别是 `deferred_proc_base_v40_cb.ko` 和
`deferred_sync_file_v40_cb.ko`。原操作表及 open/release 等生命周期入口
继续常驻，首次调用普通进程上下文回调时，通过强类型接口和
`request_module()` 加载实现。

组合结果通过真实 Clang/LLVM 内核构建、MODPOST、严格体积门禁、4 次完整
QEMU 生命周期测试以及 8 对平衡启动 A/B。它是“从 LLVM 图分析到源码自动
提取、模块生成、懒加载及运行时验证”的完整闭环，不是手工复制函数的演示。

## 为什么必须按组合做发布门禁

单独看两个候选，它们都不满足完整发布门禁：

| 候选 | 常驻对象节省 | `bzImage` 变化 | 单独门禁 |
|---|---:|---:|---:|
| `/proc/base.c` | 4,618 B | +1,280 B | 失败：镜像增大 |
| `sync_file.c` | 3,203 B | -5,088 B | 失败：不足 4 KiB |
| 两者组合 | 7,821 B | -3,808 B | 通过 |

因此排名器新增了“互补发布组合”：先按源文件聚合并扣除各自常驻桩成本，
再自动找出单组低于 4 KiB、组合后达到门槛的候选对。完整图上得到：

- 685 张识别出的回调表；
- 154 张 `READY` 表；
- 69 个源文件组；
- 54 个互补双组组合；
- 本次 `sync_file + /proc` 组合以估算净收益 6,288 B 排名第 3；
- 私有辅助函数闭包展开后，实测净收益提高到 7,821 B。

估算只用于选择顺序，不能替代最终对象、链接、压缩镜像和运行时门禁。

## 自动提取边界

### `/proc/base.c`

移动的 20 个直接入口覆盖 `auxv`、`environ`、`cmdline`、`mem`、
`oom_adj`、`oom_score_adj`、`loginuid`、`sessionid`、`comm`、
`timerslack_ns`、`timens_offsets`、LSM attr 和 `coredump_filter`。LLVM/AST
闭包又自动带走 `get_mm_cmdline`、`get_mm_proctitle`、`get_task_cmdline`、
`mem_rw` 和 `__set_oom_adj`，最终为 25 个函数。

8 个 open/release 生命周期回调继续常驻。10 个共享内核依赖通过一次绑定的
强类型依赖表传递；头文件内联的 `set_task_comm` 和
`trace_oom_score_adj_update` 使用常驻代理，不扩大模块的非类型安全查找面。

### `sync_file.c`

操作表中的 `sync_file_ioctl` 和 `sync_file_poll` 成为惰性入口。源码闭包继续
带走 merge、fence-info、fence 收集与设置等 8 个私有辅助函数，最终移动
10 个函数。被公开 API 共用的 `sync_file_alloc`、`sync_file_fdget` 和
异步回调 `fence_check_cb_func` 保持常驻，`sync_file_release` 也因生命周期
语义保持常驻。

35 个移动的 C 定义中有 25 个在基线最终 `vmlinux` 中保留独立 ELF 函数
符号，其余已被编译器内联。25 个独立符号合计 10,776 B。

## 严格体积结果

相对 v39 基线：

- 受影响内建对象的永久 allocatable 字节：38,469 → 30,648；
- 启动未加载时精确节省：7,821 B；
- 两个模块加载后的 allocatable 字节：14,147 B；
- 两个模块都加载后的受影响总占用：比原实现增加 6,326 B；
- 最终链接永久区：15,704,648 → 15,704,648 B，零回退；
- `bzImage`：5,017,376 → 5,013,568 B，减少 3,808 B。

链接器的 2 MiB 对齐仍吸收了本次代码减少。对齐前 payload 减少 8,192 B，
最终 `_text.._etext` 区间未缩页；距离当前上一条边界还需要减少 178,352 B。
所以本阶段不能声称启动永久页已经减少，精确收益应引用对象级 7,821 B。

## 运行时验证

QEMU 场景连续运行 4 次，每次 16 步，64/64 步全部通过：

- READY 时两个新模块均不存在；
- 首次 `/proc` 回调和首次 sync-file 回调分别自动加载正确模块；
- `/proc/self/mem` 的 read、write、llseek 以及策略、audit、LSM、time-ns
  回调均被调用；
- 使用真实 `dma_fence`/sync-file FD 覆盖 poll、merge、file-info 和 signal；
- 已打开 FD 在实现模块卸载后继续使用，可触发同一模块重新加载；
- 4 个进程同时首次调用时，两个模块均只形成正确的绑定状态；
- 两个模块均可卸载、再次加载；
- 日志无 BUG、Oops、WARNING、general protection fault 或 panic。

sync-file 测试夹具只在功能验证开始后手工 `insmod`，不进入生产内核，也不
参与 READY 启动资源测量。它只制造真实 fence FD；被测 ioctl/poll 仍执行
自动提取模块中的代码。

8 对、共 16 次冷启动使用相同 initramfs 和 `nokaslr`，A/B 中位数为：

| 指标 | v39 基线 | v40 | v40 - 基线 |
|---|---:|---:|---:|
| 永久内核页 | 15,336 KiB | 15,336 KiB | 0 KiB |
| READY 时间 | 1.010 s | 1.005 s | -0.005 s |
| MemAvailable | 459,872 KiB | 459,836 KiB | -36 KiB |
| Slab | 6,802 KiB | 6,800 KiB | -2 KiB |

四项均通过预设回退门禁。-36 KiB 的 MemAvailable 波动小于 128 KiB 容限，
不应解释为确定的收益或回退。

## 完整内核占比

最终 ELF 的正尺寸函数分母仍是 28,959：

| 类别 | 函数数 | 占比 |
|---|---:|---:|
| CORE | 26,732 | 92.309817% |
| READY | 81 | 0.279706% |
| BLOCKED | 296 | 1.022135% |
| UNKNOWN | 1,850 | 6.388342% |

`CORE/READY/BLOCKED/UNKNOWN` 是保守规划器的互斥分区。回调表改写能够把原
规划器判为 CORE 的函数变成“常驻桩 + 模块实现”，所以成功模块化数量是一
个经过后端门禁的正交集合，不能再作为第五类与前四类相加。

累计严格合格结果为：

- 17 个模块；
- 309 个移动的 C 函数定义；
- 200/28,959 个基线最终 ELF 函数，0.690632%；
- 对应 93,145/6,693,841 B，1.391503%；
- 内建对象累计节省 78,886 B；
- `bzImage` 相对纯 v32 从 5,056,256 降到 5,013,568 B，减少 42,688 B，
  即 0.844261%。

## “init 没调用就都能模块化吗”

答案仍然是否定的。init-cold 是必要证据，但不是充分条件：

- 模块加载器可用之前可能到达的代码不能按需加载；
- IRQ、NMI、atomic、关中断等不能睡眠的上下文不能调用
  `request_module()`；
- open/release、对象析构、回调注册和长期持有的函数地址涉及生命周期；
- 可变全局状态不能在卸载/重载时丢失或被复制成两份；
- 匿名类型、特殊 section、静态 key 的链接期常量地址等不能直接跨模块
  ABI；
- `__init` 且只在启动使用的代码应留在 init section，启动后由内核释放，
  把它改成模块通常既破坏早期启动又增加总占用；
- 最后还必须通过真实构建、体积、并发、卸载重载和启动 A/B。

另外，惰性模块默认不会自动卸载。`/proc/self/cmdline` 一类接口可能被真实
系统的监控工具很早访问；首次访问后，本阶段节省会变成模块加载后的
+6,326 B 增量。若目标是长期内存而不只是 READY 前资源，应优先选择长期
不用的功能，并另行设计有生命周期证明的安全卸载策略。

## 下一阶段

下一步应使用新组合排名器，并叠加目标发行版的真实早期用户态访问轨迹：

1. 排除会在 systemd、udev、容器或监控启动时立即触发的接口；
2. 优先组合低首次使用概率、闭包大、回调入口少的源文件组；
3. 继续累计至少 178,352 B 的对齐前 payload，跨过真实链接页边界；
4. 每个组合仍执行本阶段相同的严格对象、镜像、生命周期、并发和 A/B
   门禁，不能因追求比例而放宽安全边界。
