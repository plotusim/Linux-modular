# v32 扎实阶段成果：配置匹配的全图与八模块严格验证

## 结论

在 Linux 5.10.176、x86_64、v31 自动启动配置上，v32 已把“完整 LLVM
引用图 → 新鲜启动证据 → 候选规划 → AST 提取 → 真实内核构建 → QEMU
加载/卸载/重载 → 尺寸与启动 A/B”闭合为一条可复现链路。

此前八个模块虽然能运行，但最终链接镜像会因 ksymtab/kallsyms 和 4 KiB
对齐增加常驻页。v32 通过类型安全依赖表、静态初始化 trampoline、宏/内联
隐藏依赖的直接导出降级，以及紧凑的 48 位 Base32 ABI 名称，把八模块全部
压回“最终链接常驻区间零增长”。因此，原来统计的 45 个最终 ELF 函数不再
只是功能成功，而是同时通过严格链接门禁。

## 完整图、启动证据与真实分母

- 1,503 个与最终 `vmlinux` 链接输入精确对应的 LLVM fact stream；
- 引用图 143,300 个节点、910,007 条边；
- 混合 roaring fixed-point 指针求解后 unresolved 间接调用为 1,087；
- 新鲜 ftrace 在 loader-ready marker（1.291794 s）前观测到 4,219 个
  `BOOT_HOT` 函数；23,910 个函数为当前工作负载下的 `BOOT_COLD`；
- 最终 `vmlinux` 分母为 28,959 个正大小函数、6,693,841 字节；
- IR→ELF 精确覆盖 28,129/28,959，即 97.133879%。

最终分类如下：

| 分类 | 函数 | 占比 | 字节 |
|---|---:|---:|---:|
| CORE | 26,732 | 92.309817% | 6,353,289 |
| READY | 81 | 0.279706% | 56,123 |
| BLOCKED | 296 | 1.022135% | 42,480 |
| UNKNOWN | 1,850 | 6.388342% | 241,949 |

这里的 CORE 仍表示“当前策略下保留常驻”，不表示这些函数全部在启动期执行。
启动冷热统计与安全可模块化分类是两个独立口径。

## 依赖打包为何有效

八个 bundle 原本需要暴露 52 个常驻依赖符号。v32 将可精确改写的依赖放进
每模块一张只读强类型表，只留下 12 个依赖导出边界（8 张表加 4 个保守直接
导出）；再加 8 张模块实现 operations 表，总生成导出边界为 20。

两个真实编译问题被固化成通用机制：

1. splice 的 `pipe_buf_operations` 需要编译期常量函数地址。生成器为常驻
   函数产生同签名模块 trampoline，使静态初始化器仍引用本地函数地址；
2. setns 的头文件内联 `put_nsproxy()` 隐藏了对 `free_nsproxy` 的调用。
   `direct_resident_dependencies` 允许把该符号标记为审计过的直接导出，最终
   MODPOST 继续充当兜底检查。

依赖表本身直接作为只读变量导出，省掉一个 getter 函数和私有实例。导出表
和 loader 等运行时符号名使用 48 位 Base32 内容 ID，相关 C 类型复用同一
主干；相对于长十六进制名称，它减少 kallsyms 字符串但不降低原有 48 位
碰撞强度。不会成为运行时符号的结构体字段仍使用确定性的 64 位 ID。

## 三层尺寸门禁

| 指标 | 基线 | 八模块 | 差值 |
|---|---:|---:|---:|
| 8 个受影响 `.o` 永久段 | 65,807 B | 47,067 B | **-18,740 B** |
| 最终链接永久区间 | 15,704,648 B | 15,704,648 B | **0 B** |
| `bzImage` | 5,056,256 B | 5,046,784 B | **-9,472 B** |

八个 `.ko` 全部加载后的永久段合计为 31,698 B，届时相对基线增加
12,958 B。这符合“未使用时不付模块本体成本”的模型，不应解释为所有功能
同时使用时仍更小。

必须特别说明：18,740 B 是受影响对象内可归因的永久 allocatable section
净减少；链接脚本的分段与页对齐吸收了这部分变化，所以启动时实际永久内核
页仍是 **0 B 改善、0 B 回退**。`vmlinux` 文件本身变小也不能替代页边界
测量。下一阶段若要宣称启动内存下降，必须让最终链接区间至少跨过一个真实
页边界，或采用可在启动后释放的专用 cold-text 布局。

## 动态与启动验证

同一个 BusyBox initramfs 场景连续运行 4 次，每次都完成 8/8 步：

1. READY 时八模块均不存在；
2. 组合功能触发器自动加载全部模块；
3. 已加载路径重复执行成功；
4. 八模块全部卸载；
5. 再次调用后全部重新加载。

4 次均通过，READY 中位数为 0.505 s。

8 对平衡交错启动 A/B 结果：

| 指标 | 模块化 - 基线 | 门禁 |
|---|---:|---:|
| 永久内核汇总 | 0 KiB | ≤ 0 KiB |
| READY uptime | 0.000 s | ≤ +0.250 s |
| `MemAvailable` | +62 KiB | ≥ -128 KiB |
| Slab | +42 KiB | ≤ +64 KiB |

全部通过。`MemAvailable` 和 Slab 的几十 KiB 变化属于当前实验噪声范围，
不作为收益声明。

## 下一阶段目标

v33 不再把“更多 READY”或“更多对象字节”作为主目标，而以最终链接页为
目标函数：

1. 从 23,910 个 `BOOT_COLD` 函数、5,534,330 字节的经验池中，优先搜索
   同源且共享导出面的更大所有权闭包；
2. 将候选按 text/rodata/data/BSS 的边际链接影响组合，并在每次真实链接后
   反馈优化，而不是只累加 `.o` section；
3. 发布门槛要求最终永久区间至少减少一个真实页，同时继续满足模块未加载
   启动、功能恢复、卸载/重载和启动 A/B 无回退；
4. 把文件系统、网络、存储、容器与 LSM 工作负载加入证据矩阵，只有在所有
   目标画像中都满足阶段和上下文约束的闭包才进入通用候选集。

## 阶段边界

当前成果足以证明自动提取后端、真实内核集成和严格验证方法成立，但不代表
通用发行版可直接部署。启动证据只覆盖一份 x86_64 QEMU/initramfs 工作
负载；真实文件系统、网络、存储、容器、LSM、PREEMPT/RT、不同硬件和其他
架构都必须重新构图、采样并运行同样门禁。未解析间接调用和缺失 ELF 映射
继续保守进入 UNKNOWN，不能因启动轨迹未出现就直接移出常驻内核。
