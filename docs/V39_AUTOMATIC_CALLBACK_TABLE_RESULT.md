# v39：完整 LLVM 回调表发现与 tracefs 自动函数模块化

## 结论

v39 把 v38 的单表审计扩展成了完整内核自动发现、同源聚合、二次 ABI
可桥接性检查和真实生成。系统在 143,300 节点、910,007 条边的配置匹配
LLVM 引用图上识别 685 张回调表，其中 154 张满足当前自动安全策略，37 张
在只计算接口和包装器时为正收益。

排名第一的未处理同源集合是 `kernel/trace/trace.c`。工具从 21 张常驻
`file_operations` 表中发现 35 个未在 loader-ready 启动轨迹出现的普通
进程上下文接口，然后自动剔除两个不能安全跨翻译单元的接口：

- `tracing_stats_read` 依赖文件私有匿名类型 `trace_clocks`，Clang 的诊断
  类型拼写不是合法 C ABI；
- `tracing_mark_write` 通过 `static_branch_unlikely()` 使用常驻 static key，
  x86 jump-label 要求其地址是内联汇编立即数，不能改写成运行时依赖表地址。

其余 33 个接口形成 `deferred_trace_v39_cb.ko`，AST/LLVM 私有闭包最终移动
43 个 C 函数和只读 `readme_msg`，总源码 40,003 B。21 张回调表、open、
release 以及可变持久状态都留在核心。模块缺失时，每次 read/write/poll/
splice/llseek 包装器可请求模块、持有模块引用完成调用，然后释放引用。

## 为什么“init 阶段没调用”不等于“都能直接模块化”

理论上，loader-ready 前没有执行的函数属于启动冷候选池；它说明把函数放进
未加载模块不会直接破坏已观测启动路径。但它不是充分条件。自动提取还必须
同时满足：

1. 第一次可能调用发生在模块加载器可用之后，且上下文允许睡眠；IRQ、NMI、
   atomic、关中断路径不能现场 `request_module()`。
2. 常驻对象保存的函数地址必须继续有效。本项目保留回调表及薄包装器常驻，
   只移动包装器后的实现。
3. open/release、VMA、work、timer、RCU 等跨调用生命周期必须闭合；不能在
   模块卸载后留下指向模块文本或数据的地址。
4. 可变状态必须有明确唯一所有者。随模块卸载丢失状态会改变语义，和启动
   是否调用无关。
5. 跨模块依赖必须有可表示的 C ABI 和合法导出。匿名类型、特殊 section、
   weak/汇编实现、static-key 立即数等需要专门代理或保持常驻。
6. 最终仍要通过 Kbuild、MODPOST、严格尺寸门禁、卸载并发测试和启动 A/B。

因此正确命题是：

> init-cold 是扩大候选集合的必要动态证据；引用闭包、上下文、生命周期和
> ABI 可桥接性共同决定其中哪些函数能变成按需模块。

另外，只在 init 使用、之后永不再用的函数通常应放进 `__init`，由
`free_initmem()` 自动回收；模块化更适合“启动不用、运行期偶尔需要”的代码。

## 完整图排名

LLVM `GLOBAL_INITIALIZER` 原始事实包含 73,906 条本地函数边。按同一聚合槽
去重后移除 41,116 条重复证据，得到 32,790 个唯一目标和 15,044 个含本地
函数初始化器的全局对象。结构布局和字段偏移恢复后：

| 分类 | 回调表数 |
|---|---:|
| 自动 READY | 154 |
| 需要人工/专用生命周期模型 | 407 |
| 没有安全冷接口 | 124 |
| 总计 | 685 |

37 张 READY 表的接口级估算净收益合计 33,210 B。这只是排序值，不是已实现
收益。`trace.c` 同源集合原有 35 个接口、11,420 B 已知函数文本，按 640 B
首包装器和每新增接口 96 B 估算净值 7,516 B。二次可桥接检查留下 33 个
接口、10,024 B 直接文本，估算净值 6,312 B；真实闭包和只读全局使最终
对象收益更高。

## 新增自动化

- `rank-callback-tables` 扫描完整图，按表和源文件两级去重、分类、估算并输出
  JSON/Markdown 排名。
- `prepare-callback-table` 不再要求先有 syscall 候选；它合成可审计 READY
  候选，把同源多表打包，然后调用原有 AST/LLVM 闭包与后端。
- 生成后自动追踪每个接口的模块侧依赖。如果仅某接口到达匿名类型或
  static-key 常量地址约束，只排除该接口并重新生成，不放弃整组。
- SourceExtractor 的全局声明范围现在能跨过未激活的 `#if` 分支，扫描到真实
  结尾分号；这修复了 `readme_msg` 条件字符串被截断的问题。
- 新增 tracefs 运行触发器，覆盖配置同值读写、llseek、poll、非阻塞 read/
  splice、FD 跨卸载重载和四路并发首次绑定。

## 严格尺寸结果

基线是同配置、同编译器、同构建元数据的 v38 内核，不使用跨配置数字：

| 指标 | v38 基线 | v39 | 变化 |
|---|---:|---:|---:|
| `trace.o` 永久 allocatable bytes | 108,694 | 98,870 | **-9,824 B** |
| `bzImage` | 5,022,624 | 5,017,376 | **-5,248 B** |
| 最终 `vmlinux` 永久链接区间 | 15,704,648 | 15,704,648 | 0 B |
| 模块加载后的永久 bytes | 0 | 16,388 | +16,388 B |
| 全部加载相对基线 | — | — | +6,564 B |

这说明项目优化的是未使用功能不加载时的常驻体积；使用 tracefs 后会支付
模块成本。增量严格门禁要求对象至少减少 4 KiB、压缩镜像不增长、最终链接
区间不增长，三项全部通过。

相对 v32 同配置纯函数模块化基线，严格集合现在有 15 个模块、274 个迁移 C
函数定义，对应 175/28,959 个基线最终 ELF 函数（0.604303%）。受影响对象
累计减少 71,065 B，`bzImage` 从 5,056,256 B 降到 5,017,376 B，即
**-38,880 B（-0.768948%）**。早先跨配置得到的约 48% 数字不属于函数提取
收益，不能用于本项目结论。

## 链接对齐与启动资源

v39 又让 2 MiB 对齐点之前的 payload 减少 4,096 B；从 v32 起累计减少
69,632 B。但链接器把它转换成等量 padding，最终 `_text.._etext` 仍没有缩短。
距离跨过上一条对齐边界还需约 186,544 B，因此本轮明确声明最终启动常驻页
减少 **0 B**。

运行验证结果：

- 4/4 轮、每轮 10/10 步生命周期场景通过；
- READY 时模块不存在，首次 tracefs 操作自动加载；
- 已打开 README FD 跨过 `rmmod`，同一 FD 后续 read 自动重载；
- 4 路并发首次使用、再次卸载/重载全部通过；
- dmesg 无 BUG、Oops、WARNING、GPF 或 panic；
- 8 对、16 次平衡交错启动 A/B 通过；永久内核 KiB 差值为 0，READY 中位
  时间差为 -0.015 s，`MemAvailable` 差值 -126 KiB，在 512 KiB 噪声门限内。

## 下一步

当前最高价值的机制工作不是取消安全检查，而是生成“常驻表达式代理”：例如
让常驻 helper 执行 `static_branch_unlikely(&key)`，模块只调用一个可导出的
布尔代理。该优化能安全收回被 static-key 约束阻塞的函数。随后按完整图排名
依次评估 `fs/proc/base.c`、SELinux、sync-file 等同源组，并继续要求相同七类
门禁。想让 QEMU 启动常驻页出现可见下降，当前至少还需把 186,544 B 的
对齐前 payload 安全移出核心。
